# 归因模型｜Attribution Model

归因模型回答的不是：

> “这个成果是不是他的？”

而是：

> **“这个人在这项活动里真正承担了什么角色？”**

这一区分在 AI Agent 参与软件开发后尤其重要。

---

## 为什么简单的作者归因不够

公开痕迹通常只能看到：

```text
某人拥有仓库
某人提交了 PR
某个 PR 被合并
某个项目用了 Rust
```

但同一个 GitHub 结果背后可能存在完全不同的过程：

### 情况 A

本人发现问题、设计方案、实现、测试，AI 只查资料。

### 情况 B

本人定义问题和方案，AI 完成大部分代码，本人负责审阅和验证。

### 情况 C

AI 从寻找 Issue、分析、实现、测试到解释 Review 基本全程推进，本人主要负责发起、授权和必要操作。

GitHub 页面可能看起来很相似，但对应的个人能力画像应该明显不同。

因此：

> **Artifact ownership is not role attribution.**  
> 成果归属不等于活动角色归因。

---

# V0 角色集合｜Human Roles

第一版只记录少量高价值角色，不追求穷尽所有行为。

## `initiated`｜发起

这个人是否主动决定开始这件事。

例：决定做一个项目、参与一个 Issue、修复一个问题。

## `selected`｜选择

是否由本人判断“做哪一个问题 / 采用哪个方向”。

如果任务完全由 AI 推荐并直接推进，`selected` 可能较弱。

## `specified`｜定义目标 / 需求

是否由本人定义“想解决什么”“结果应该是什么样”。

这不等于能够设计技术实现。

## `implemented`｜实现

是否亲自完成核心代码、配置、文档或其他具体产出。

这是最容易被 Artifact 错误放大的角色，因此默认不能从仓库所有权直接推断。

## `reviewed`｜审阅

是否主动阅读实现并对质量、技术方案或变化范围做判断。

仅仅点击 Merge、复制 AI 结论或让 AI 解读 Review，不应自动视为强审阅证据。

## `validated`｜验证

是否本人能够判断结果是否真正解决问题，例如：

- 运行并观察真实行为；
- 发现回归；
- 比较预期和实际结果；
- 判断测试是否覆盖了关键需求。

“测试由 AI 编写”与“用户能够有效验证结果”可以同时成立。

## `operated`｜操作

是否执行了必须由本人完成的现实操作，例如：

- 授权 GitHub；
- 创建仓库；
- 手动测试真实设备；
- 点击需要本人身份的操作。

操作本身通常是弱能力证据，但能帮助还原真实过程。

## `authorized`｜授权

是否提供权限、确认高风险动作或批准 Agent 继续执行。

它证明用户处于流程中，但通常不能单独支持技术能力判断。

## `debugged`｜调试 / 定位

是否本人参与寻找根因、提出假设、排除错误路径。

这是比“项目存在”更强的能力证据。

## `explained`｜解释

是否能够用自己的话解释：

- 问题为什么发生；
- 为什么采用某个方案；
- 修改会带来什么影响；
- 为什么测试可以证明它正确。

解释是理解的重要证据，但一次解释仍不等于长期掌握。

# 角色状态｜Role State

V0 不使用百分比。

每个角色只使用：

```text
supported   有明确证据支持
partial     有部分证据，但不足以稳定确认
low         已知参与很少或主要由他人 / AI 承担
unknown     当前资料无法判断
```

不要使用看似精确的 `73%`、`0.82` 等数字。

---

# Agent 角色｜Agent Roles

当用户明确说明 AI Agent 的参与方式时，可以用同样思路记录 Agent 主要承担的工作：

```text
discovery       寻找任务 / Issue
analysis        分析问题
planning        设计实现路径
implementation  具体实现
testing         测试与回归
interpretation  解读 Review / 错误 / 文档
operation       代理执行工具操作
```

这不是为了计算“AI 占比”，而是为了避免把 Agent 的行为错误归因给用户。

# 关键推理规则

## 规则 1：参与证据不能自动升级为执行证据

```text
PR author
→ 可以证明参与
→ 不能直接证明 implemented
```

## 规则 2：外部接受验证的是结果，不自动验证人的全部能力

```text
Merged PR
→ delivered outcome 被接受
→ 不等于每个底层知识都由本人掌握
```

## 规则 3：低实现归因不意味着“什么都没有”

例如：

```text
implemented: low
validated: supported
specified: supported
```

仍然可以支持：

- 需求判断；
- 产品判断；
- 验收能力；
- AI-assisted workflow；

只是不能支持对应的独立编码能力。

## 规则 4：角色归因优先改变 Claim，而不是删除历史

校准后不应该说：

> “这个 PR 不属于用户了。”

而应该说：

> “PR 仍然属于他的真实经历，但它支持的能力判断发生了变化。”

---

# 校准原则

角色归因通常无法完全从 GitHub 被动推断，因此允许用极低成本的 Micro Calibration 补充。

优先询问能覆盖多个活动的概括性问题，例如：

> **你在这些开源 PR 中通常更接近哪种参与方式？**

而不是逐个 PR 询问。

一次答案应该尽可能同时更新多个 Claim 和 Knowledge Node。

# 当前研究问题

后续需要继续验证：

1. 哪些角色真的值得进入 V0，哪些过细；
2. 哪些 GitHub 行为可以安全地为某些角色提供弱证据；
3. 如何识别用户本人真实的 `validated` / `debugged` 行为；
4. 如何避免用户为了“让星图更亮”而美化自我报告；
5. 同一个人不同项目中的角色差异应该如何聚合。
