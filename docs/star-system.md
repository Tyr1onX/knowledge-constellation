# 星体系统｜Star System

> 这份文档描述 Knowledge Constellation 当前的星体视觉语言。它属于内部设计规范，不应直接出现在最终产品首屏。

## 核心原则

星体不能只是“数据点换成发光圆”。

每一种星体形态都必须同时满足两件事：

1. 远看像一个真实宇宙中的对象；
2. 近看能够承载 Knowledge Model 的差异，但不能把视觉强弱误导成能力高低。

因此，星体的主要视觉语义是：

```text
存在感      → representativeness / 当前人物轮廓中的代表性
清晰程度    → resolution / 当前被看清的程度
星体类型    → structural role / 当前结构角色
动态状态    → formation / recency / 当前是否正在形成
```

能力深度本身不直接映射为星体大小。

---

# 1. Core Star｜核心星

用于当前人物轮廓中最稳定、最有解释力的主题节点。

视觉特征：

- 明确光核；
- 较紧致 corona；
- 少量衍射星芒；
- 外部轮廓稳定；
- 不使用复杂动画制造“高级感”。

它表达：

> 这颗星对当前人物轮廓很重要，而且系统知道它为什么存在。

它不表达：

> 这个人的该项能力一定很强。

---

# 2. Forming Star｜正在形成的星

用于明确处在学习、建立、反复实践中的节点。

视觉特征：

- 有稳定光核；
- 周围存在非常轻的物质环 / 轨迹；
- 环缓慢旋转或呼吸；
- 不能做成游戏技能升级特效。

它表达：

> 这里正在形成结构，而不是已经完成。

---

# 3. Veiled Star｜被雾包裹的星

用于 `high representativeness + low resolution`：

> 这项技术/主题明显属于这个人的经历，但我们对个人能力、角色或独立程度还看不清。

典型例子：

- 核心项目长期使用某技术；
- 但实现归因不明；
- AI / 协作参与程度尚未解析。

视觉特征：

- 星体本身可以有明显存在感；
- corona 更宽、更散；
- 周围存在非规则薄雾；
- 外环可以断续；
- 光核仍然存在，避免把“未知”画成“没有”。

这是 Knowledge Constellation 最重要、也最有辨识度的星体之一。

---

# 4. Bridge Star｜桥梁星

用于连接多个节点、活动或星系的结构性节点。

它的关键不是“水平高”，而是：

> 删除它以后，多个主题之间的结构解释会明显变弱。

视觉特征：

- 光核明确；
- 较细、方向性更强的星芒；
- Hover 时更容易显出连接关系；
- 平时不常驻大量关系线。

---

# 5. Trace Star｜外围痕迹

用于真实出现过，但不足以定义当前人物轮廓的节点。

例如：

- 一次 PR 中出现的 CAS；
- 某个项目环境里的 SQLite WAL；
- 偶然接触的单次工具。

视觉特征：

- 很小；
- corona 弱；
- 不抢占画面中心；
- 缩放或进入局部后才值得注意。

原则：

> 技术看起来越“高级”，越不能因为名字本身获得更强视觉权重。

---

# 6. 星云不是分类边框

Galaxy 不使用：

- 椭圆边框；
- 卡片分组；
- 固定色块背景；
- 永久显示的大标题。

目前优先通过：

- 局部星尘密度；
- 不规则、低饱和云气；
- 空间距离；
- 色温倾向；
- Hover / Focus 时才出现的名称；

让用户感知星系。

Galaxy 应当像一个空间区域，而不是 dashboard section。

---

# 7. 关系线默认不存在于第一眼

关系线属于 exploration layer。

默认：

```text
宇宙
```

Hover / Focus：

```text
当前星体
   ↓
少量真实关系显现
```

不要把所有关系永久铺开，否则画面会退化成 network graph。

---

# 8. 文字按交互逐层出现

```text
Initial
几乎只有宇宙

Hover
星名 + 极短状态

Click
简短解释

Deep explain
为什么这样判断 / 哪些地方仍不清楚
```

开发术语、模型字段、Evidence ID、V0 状态等不得进入默认产品表面。

---

# 9. 当前下一步

在当前星体语法稳定后，再继续研究：

1. 星云形态与真实空间层次；
2. 更自然的星系构图；
3. Focus / Zoom 的镜头语言；
4. 跨星系桥接关系如何在交互中出现；
5. 同一个人不同解析度下，星体如何“显影”而不是简单变大/变亮。
