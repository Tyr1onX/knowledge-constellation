# Presentation Contract｜成品界面契约

> 最终产品首先是一幅“属于这个人的知识宇宙”，其次才是一份可解释的数据报告。

本文件约束 **Knowledge Model 如何进入最终用户界面**。它的目的，是防止研究阶段、调试阶段和模型内部使用的语言直接泄漏到成品体验中。

## 1. 第一眼必须先是宇宙

打开最终产物时，用户首先应该感受到：

- 空间；
- 星体；
- 星系；
- 密度与疏密；
- 某些区域更清晰、某些区域仍在雾中；
- 这是“我的”结构，而不是一张报告。

第一屏默认不出现：

- V0 / Prototype / Passive-only 等开发阶段标签；
- “当前暗区”“Evidence E1/E2”之类模型术语；
- 解释图例；
- 大面积侧边栏；
- 调试按钮；
- 长段产品原则说明。

这些内容即使对研发有用，也不属于用户第一眼。

## 2. 信息按交互逐层出现

推荐层级：

```text
默认
只有宇宙本体
    ↓ hover
星名 / 星系名 / 极短状态提示
    ↓ click
节点解释卡片
    ↓ deeper inspect
证据、来源、归因、不确定性细节
```

即：

> **远看是作品，近看是工具。**

## 3. Product Surface 与 Inspector 分离

最终实现应区分两种模式：

### Product Surface｜用户表面

只放用户真正需要感受到或操作的内容。

### Inspector｜解释 / 调试层

用于查看：

- Source；
- Evidence；
- Attribution；
- Confidence；
- Resolution；
- 结构推导；
- 模型版本；
- 调试信息。

Inspector 可以存在，但不能默认占据视觉中心。

## 4. 文字默认克制

### 默认状态

- 节点名称不必全部常驻；
- 星系名称可以非常轻，甚至只有靠近时出现；
- 绝不在画面边缘常驻解释性段落。

### Hover

只显示：

```text
JavaScript / DOM
正在形成
```

不要直接显示完整解释。

### Click

才展开：

- 为什么它存在；
- 当前知道什么；
- 还不知道什么。

## 5. 星体必须有自己的视觉语言

星星不能只是相同圆点换大小。

至少需要研究：

- 核心亮点；
- halo / corona；
- 星芒；
- 模糊边缘；
- 星尘；
- 活跃脉冲；
- 第二层小星；
- bridge node 的特殊位置关系。

但这些视觉差异必须有稳定语义，不能为了“更炫”随意映射能力等级。

## 6. 首屏视觉语义

V1 暂定：

- **视觉存在感** → 代表性（Representativeness）
- **边缘清晰度 / 核心稳定度** → 解析度（Resolution）
- **空间距离** → 结构关联强弱
- **星云 / 区域密度** → Galaxy / Motif
- **轻微动态** → 当前活跃或正在形成

能力深度不要在总览里被压成“星体大小”。

## 7. 星系边界不要像图表分组框

避免：

- 虚线椭圆；
- 卡片框；
- 明确的矩形分区；
- 类似流程图的容器。

更倾向：

- 星云浓度；
- 局部背景色差；
- 星尘密度；
- 空间聚类；
- 弱标签；
- 视线自然形成的区域感。

目标是“感知到星系”，不是“看到三个被圈起来的组”。

## 8. 最终成品禁止开发语句泄漏

以下语言只属于研发文档或 Inspector：

- Passive-only；
- V0 / V0.1；
- 当前模型；
- Evidence E1；
- 这是一个 Prototype；
- 本图不代表……；
- 这一层用于测试……；
- 当前暗区；
- 模型尚未确认……（除非用户主动打开解释）。

成品不应让用户感到自己正在看一个开发者调试页。

## 9. 当前优先级

内部 Recognition / Attribution / Structure 模型已经达到可以支撑第一轮视觉验证的程度。

下一阶段优先：

1. 建立真正的 Universe-first 视觉；
2. 降低常驻文字；
3. 设计有辨识度的星体；
4. 验证星系是否能靠空间与星云被感知；
5. 再根据视觉反馈反推 Distillation 和 Structure。

因此接下来不是“内部模型完成后再做视觉”，而是：

> **内部模型冻结一个可用基线 → 视觉原型 → 视觉暴露新问题 → 再反哺模型。**
