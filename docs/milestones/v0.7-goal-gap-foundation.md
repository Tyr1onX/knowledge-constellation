# v0.7 — Goal / Gap Foundation

Status: **implementation checkpoint — awaiting clean human semantic validation**

## Product question

After a Current Universe answers “what can the available evidence support about me now?”, the next product question is:

> Given a concrete goal, what does that goal actually require, where does my current evidence already connect, and what are the next 1–3 things most worth advancing?

## Implemented chain

```text
Completed Current Recognition
+
Goal + target-side sources
↓
Pass E — Target Model
↓
Pass F — Current-to-Target Gap
↓
Pass G — Next 1–3 Steps
```

New contracts:
- `kc.goal-input.v1`
- `kc.target.v1`
- `kc.gap.v1`
- `kc.plan.v1`

New harness:
- `harness/goal_pipeline.py`
- `harness/validate_goal.py`
- `harness/goal_e2e.py`

## Locked boundaries

1. **Target independence** — Pass E cannot read the current person's Model. The target cannot move toward the person merely to make the gap look smaller.
2. **Absence is not inability** — missing current evidence becomes `not_observed`, not “cannot do”.
3. **Gap is not a score** — no fake 0–100 competency percentages.
4. **Planning does not rewrite current truth** — recommendations never upgrade current Claims/Nodes/Scene.
5. **1–3 next steps** — this is prioritization, not another generic roadmap.
6. **Eligibility is separate** — degree/location/work authorization/etc. do not become study topics.
7. **Progress requires new evidence** — the Current Universe grows only after real new Source material enters Recognition again.
8. **Preview isolation** — repository preview/showcase Scenes are demo outputs, never valid runtime semantic inputs or substitutes for a fresh Current Recognition run.
9. **Auditable Goal output** — when the repository runtime is available, user-facing goal advice must come from accepted `target.json`, `gap.json`, and `plan.json`, not an improvised prose roadmap.

## First blind-test finding — 2026-08-19

A fresh Codex received an ordinary request containing the Skill URL, the subject's GitHub profile, and a Linux/C++ backend internship goal. The textual Goal/Gap advice was directionally strong: it separated current evidence from target needs, identified C++/Linux as the central gap, and returned three priorities rather than a full curriculum.

However, the Current Universe delivery **failed the clean-generation requirement**. Codex noticed that `preview/scene.json` already contained an accepted Tyr1onX Scene and reused that repository preview instead of running a fresh Recognition chain. The delivered HTML pointed directly at the repository preview Scene.

This invalidates that run as a clean v0.7 acceptance test even though the prose recommendation was useful. The failure exposed a product/runtime boundary that was previously implicit.

Repair added after the finding:
- `SKILL.md` now states that repository previews/showcases are demo-only and may never substitute for a fresh run, even for the same subject;
- `skill/ORCHESTRATION.md` explicitly includes preview/showcase isolation;
- `harness/verify_delivery.py` rejects generated pages that point at `preview/scene.json` and checks current-run subject provenance;
- `harness/e2e.py` now runs delivery verification after building the site;
- Goal Target guidance now prefers exact internship/campus sources over adjacent full-time/social roles;
- regression tests lock these boundaries.

A fresh blind rerun is required before v0.7 can be accepted.

## Why Target / Gap is not in the Renderer yet

The accepted visual baseline is deliberately protected. Goal semantics are new and have not yet passed a clean real-user test. We therefore keep Target / Gap as a semantic companion instead of inventing a Target Universe visual language prematurely.

## Acceptance test still required

Use a real completed personal constellation and follow it with one ordinary-language goal, without exposing internal schemas or prompting tricks.

Acceptance questions:
- Was the Current Universe produced from the current request rather than copied from a repository preview/showcase?
- Do accepted `target.json`, `gap.json`, and `plan.json` exist behind the user-facing advice?
- Did Codex identify the target requirements from real target-side sources rather than a generic roadmap?
- Did `supported / partial / unresolved / not_observed` feel truthful?
- Did it avoid reading absence as inability?
- Were the chosen 1–3 next steps meaningfully better than a generic learning list?
- Did each next step connect to an existing foothold and explain what future evidence would demonstrate progress?

Only after this human semantic checkpoint passes should Target / Gap receive dedicated visual treatment.
